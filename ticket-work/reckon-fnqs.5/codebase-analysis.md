## 1. Current `rk todo add` / `addDurableTodo`

- Command: `internal/cli/todo.go:88-94` (`todoAddCmd`, `Use: "add <text...>"`, `Args: cobra.MinimumNArgs(1)`, `RunE: runTodoAddE`).
- `runTodoAddE` (`todo.go:269-329`): body is built at `todo.go:278` as `strings.TrimSpace(strings.Join(args, " "))` — argv is space-joined into one line. This is the exact "no body path exists yet" gap the ticket names. Empty check at `todo.go:279-281`.
- Dispatches to `addDurableTodo` (default) or `addEphemeralTodo` (`--ephemeral`) at `todo.go:313-318`.
- `addDurableTodo(todosDir, author, body, scheduled, deadline, depends, repeat string)` — `todo.go:337-381`. Builds node via `node.NewNode("todo", author, body+"\n")` (`todo.go:347`), sets `Props["state"]="open"` plus optional scheduled/deadline/repeat, renders, re-parses, writes via `writeFileAtomic`. **`body` is a single opaque string param — multi-line text passed in here would already flow through untouched** (see §4); the missing piece is entirely upstream, in how `runTodoAddE` builds that string from flags/args/stdin.
- `--ephemeral` branch → `addEphemeralTodo` (`todo.go:393-432`). Doc comment at `todo.go:386-392` is the "checkbox container, single-line" logic the ticket points at (ticket's `todo.go:387` — line numbers have drifted slightly since fnqs.3 landed but this is the right function): each ephemeral item is one `- [ ] text` checklist line; the container's body is split line-by-line (`splitChecklistLines`, `todo.go:977-993`), so an embedded `\n` in `text` would corrupt the checkbox parse. **Confirms ticket's scope note: -m/--edit/stdin apply only to the durable path; ephemeral stays single-line by construction.** `runTodoAddE` already rejects `--ephemeral` combined with durable-only flags (`todo.go:283-285`) — the new multi-line flags should join that guard.

## 2. `rk add` is NOT an ephemeral/durable dispatcher — ticket description is imprecise

- `rk add` = `addCmd`, registered at `internal/cli/root.go:103` as its own top-level command (sibling of `todoCmd`, not a child). It is the **v1-T4 log-capture verb** (`internal/cli/add.go:29-42`): appends a timestamped, authored entry to `log/<date>.md`. It has nothing to do with ephemeral vs. durable todos — that split lives entirely inside `rk todo add`'s `--ephemeral` flag (§1).
- `rk add`'s body construction is the same shape as the bug this ticket fixes: `runAddE` at `add.go:90` does `body := strings.TrimSpace(strings.Join(args, " "))` — single line, no multi-line path.
- `rk add` additionally forbids a body/author containing an embedded `## ` line (`embeddedHeaderRe`, `add.go:69`, checked at `add.go:94-96` and again for author at `add.go:87-89`) because entries are appended to a shared day file and a literal `## ` would be mis-parsed as a new day-file section header on re-parse (see `node/logparser.go`'s day-file format). **Any multi-line body from `-m`/`--edit`/stdin fed into `rk add` must still pass this guard** — a pasted multi-line body containing a markdown `## Heading` line must be rejected with the existing error, not silently corrupt the day file.
- [OPEN] The ticket's "Done when" criterion only names `rk todo add`. Scope text says "mirroring git" and titles the ticket "... for `rk todo add` / `rk add`", implying both get the flags, but only `rk todo add`'s node-per-file shape has an obvious "first body line = subject" home (via fnqs.3's `deriveTitle`, todo-type-gated, see §7). `rk add`'s day-file entries have no subject/title convention at all today (`node/logparser.go` entries are just timestamped author+body blocks). Confirm with a human whether `rk add` truly needs `-m`/`--edit`/stdin (likely yes, for multi-line log entries — the entry's body just stays multi-line prose with no subject extraction), or whether scope is `rk todo add` only and the ticket title is loose.

## 4. Reading stdin — no prior art, use `cmd.InOrStdin()`

- `grep -rn "os.Stdin"` repo-wide hits exactly one call site: `internal/cli/interactive.go:17`, `isCharDevice(os.Stdin) && isCharDevice(os.Stdout)` — a TTY-detection check for guarding the Bubbletea TUI (`isInteractive`, used by `promptGuard`, `interactive.go:32-37`), not a body-reading path.
- No test file anywhere calls `RootCmd.SetIn(...)` (`grep -rn "SetIn\b"` repo-wide: zero hits) — cobra's `Command.SetIn`/`InOrStdin()` machinery is unused today.
- **Recommendation for the implementer**: read the `'-'` stdin body via `io.ReadAll(cmd.InOrStdin())`, not `os.Stdin` directly. `cmd.InOrStdin()` defaults to `os.Stdin` when unset, so production behavior is identical, but it lets Phase-3 tests inject a fake reader via `RootCmd.SetIn(strings.NewReader(...))` — exactly how `SetOut`/`SetErr` are already faked in `runTodo` (`todo_test.go:110-111`). **`resetCLIFlags()` (`query_test.go:100-109`) does not currently reset `RootCmd.SetIn` — add `RootCmd.SetIn(nil)` there when this lands**, or a stdin reader injected by one test will leak into the next `Execute()` call within the same test binary (mirrors the exact `SetOut`/`SetErr`/`SetArgs` reset already done for that reason, see `query_test.go:95-99`'s comment).

## 5. `node.Parse`/write path is byte-preserving; multi-line body already flows through untouched

- `internal/node/node.go:1-9` doc comment: `Node` is a byte-preserving view; `Serialize()` (`node.go:143`) returns `Raw` verbatim; round-trip identity (`parse(serialize(parse(f))) == f`) is a **gated invariant**, fuzzed (~396k execs, 0 failures per the package doc).
- `Render()` (`internal/node/render.go:32-115`) is the create-path primitive `addDurableTodo` already uses: after emitting frontmatter it does `out.WriteString(n.Body)` (`render.go:113`) — **no line-splitting, joining, or escaping of `Body` happens anywhere in Render**. A `Body` string containing `"subject\n\nmore detail\n"` renders exactly as given.
- No existing CLI command constructs a multi-line `Body` today. `noteBodyFlag` (§3) is the closest — a single `--body` string, not paragraph-joined from multiple flags — but it demonstrates the trailing-newline convention (`note_v1.go:257-259`) that `addDurableTodo` should mirror: ensure the final rendered body ends with exactly one `\n` regardless of how it was assembled (currently hardcoded via `body+"\n"` at `todo.go:347`, which would double up if the assembled multi-paragraph body already ends in `\n` — check for existing trailing newline before appending).
- **Paragraph-join recommendation**: for `-m` (repeatable), join collected values with `"\n\n"` (git's convention: each `-m` is one paragraph). Watch the "Unconditional Newline Join with Optional Strings" anti-pattern documented at `docs/REVIEW_PATTERNS.md:879-901` (reckon-qxem) — if an empty `-m ""` value is allowed through, a plain `strings.Join(msgs, "\n\n")` would produce a phantom blank paragraph; either reject empty `-m` values outright or filter them before joining. The ticket requires "Subject line must be non-empty," which covers the first `-m` but says nothing about later ones — decide and document whether a blank later `-m` is an error or silently dropped.
- **"Subject line must be non-empty" is cross-cutting, not `-m`-specific.** It applies identically to `--edit`'s scratch-buffer content and to the `'-'` stdin body. Don't scatter three separate checks — assemble the body from whichever path was used, `strings.TrimSpace` it, and route it through the **existing** empty-body guard already at `todo.go:279-281` (`if body == "" { return fmt.Errorf(...) }`). Because `deriveTitle` (§7) skips leading blank lines, "the assembled, trimmed body is non-empty" is exactly equivalent to "the subject line is non-empty" — one check after assembly covers all three entry paths, no per-path duplication needed.

## 7. `title`/subject derivation (fnqs.3, already shipped — read path is NOT this ticket's work)

- `deriveTitle(body string)` — `internal/index/title.go:8-15`: first line non-blank after `strings.TrimSpace` (also strips CRLF `\r`), scanning `strings.Split(body, "\n")`. This is what "first non-empty body line = subject" means operationally — **the multi-line body this ticket assembles just needs its first line to be the intended subject; no other formatting is required for `deriveTitle` to pick it up correctly.**
- Called only at reconcile time, todo-type-gated: `internal/index/reconcile.go:270-279` (`if <type is todo> { title = deriveTitle(n.Body) }`, comment at line 270-271 confirms note/other types don't get this treatment). Stored in the `_nodes.title` column.
- `rk todo list`'s durable `Pretty()` output **already uses `Title`, not `Body`**: `todo.go:193` (`fmt.Fprintf(&b, "\n  %s [%s] %s", it.ID, it.State, it.Title)`) and JSON exposes both `Title` (`todo.go:169`) and full `Body` (`todo.go:168`). `listDurableTodos` (`todo.go:497-550`) reads `title` straight from the `nodes` SQL view (`todo.go:498,546`).
- **Consequence for this ticket**: the ticket's "Done when: `rk todo list` shows only the subject" criterion is **already satisfied by existing fnqs.3 code**, provided the index is reconciled after the write (`rk todo list` calls `ix.Reconcile()` itself, `todo.go:470-472`, so no extra step needed) and provided this ticket's new body-assembly logic puts the subject on line 1. Nothing in `today.go`/`todo.go`'s list/render path needs to change — confirmed by reading `today.go:290-305`, which only consumes the already-derived `c.title`/`c.body`, doing no line-splitting itself.
