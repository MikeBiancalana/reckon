# Codebase Analysis: reckon-fnqs.7 — Interactive create flows over the v1 verbs

## 1. Prompt/RunPrompt/Wizard/TTY-guard layer (fnqs.6, merged PR #163)

All in package `internal/tui/components`.

- `Prompt[T any]` interface — `internal/tui/components/prompt.go:9-21`. `Init() tea.Cmd`, `Update(tea.Msg) (Prompt[T], tea.Cmd)`, `View() string`, `Result() T`, `Done() (finished, canceled bool)`. Each concrete component implements this directly on itself (no adapter type) — `var _ Prompt[T] = (*Concrete)(nil)` holds per component.
- `RunPrompt[T any](p Prompt[T], opts ...tea.ProgramOption) (result T, ok bool, err error)` — `prompt.go:78-99`. Opens exactly one `tea.Program`. Checks `components.PromptGuard` (a `var func() error`, nil by default) before opening the program. `opts` is how tests inject `tea.WithInput`/`tea.WithOutput`; production call sites pass none.
- `components.PromptGuard` — `prompt.go:39`, package-level `var`, wired once from `internal/cli/interactive.go:40` (`init()`), so `components` never imports `cli`.
- `components.IndexRow{ID, Title, Type string; Props map[string]string}` — `prompt.go:27-32`. Shared display row for both pickers (TaskPicker, NotePicker); decouples `components` from `node`/`index`.
- `Wizard` — `internal/tui/components/wizard.go`. `NewWizard(steps ...StepFactory) *Wizard` (:72), `Step[T any](key string, factory func(prior map[string]any) Prompt[T]) StepFactory` (:51), `(w *Wizard) Run(opts ...tea.ProgramOption) (map[string]any, bool, error)` (:166-168, itself just calls `RunPrompt[map[string]any](w, opts...)`). Chains heterogeneous `Prompt[T]` steps via a type-erased `wizardStep`; results land in one `map[string]any` keyed by each step's `key`.
  - Each `StepFactory` closure must call the component's own `Show(...)` itself (priming point) and may read `prior[key]` to pre-fill state — bubbletea's own `Init()` is never re-invoked by the outer host for an inner step, so `Wizard.Update` calls the newly-mounted step's `Init()` explicitly on every transition (:128, :142).
  - Esc/cancel semantics: canceled at step 0 aborts the whole flow (`Done()` reports `canceled=true`, zero result); canceled at step >0 **steps back** one step, re-mounting it from its factory (:130-142). **There is no third "skip this step, keep going" signal** — see §3 gap discussion below, this is the central design fork for the planner.
- TTY guard — `internal/cli/interactive.go`. `isInteractive` is a package `var func() bool` (:16-18, stubbable in tests, mirrors `todoNow` at `todo.go:33`), true only when both stdin and stdout are real char devices. `promptGuard()` (:32-37) returns an error naming `--no-input` when `noInputFlag || !isInteractive()`. `--no-input` is `RootCmd.PersistentFlags().BoolVar(&noInputFlag, ...)` at `internal/cli/root.go:99`.
- The guard lives **inside** `RunPrompt`/`Wizard.Run`, not on `RootCmd.PersistentPreRunE` — verbs that never prompt pay nothing (`interactive.go:28-31`).

## 2. How reckon-6k0l wired `rk todo list` (merged PR #166) — the template to mirror

Files: `internal/cli/todo_browse.go` (new), `internal/cli/todo.go` (dispatch insertion), `internal/tui/components/todo_browser.go` (new component).

Pattern:
1. A pure predicate decides TUI-vs-classic **before** any RunE side effect: `todoListWantsTUI(cmd *cobra.Command) bool` (`todo_browse.go:19-32`) — `false` if `!isInteractive()`, `false` if any output-shaping flag (`all/state/durable/ephemeral`) has `cmd.Flags().Changed(name)==true`, `false` if `jsonFlag || ndjsonFlag`. **Deliberately does not check `--no-input`** — that must still reach `PromptGuard` inside `RunPrompt` so a real TTY + `--no-input` errors instead of silently falling back (`todo_browse.go:16-18` comment).
2. `runTodoListE` (`todo.go:452-456`) branches at the top: `if todoListWantsTUI(cmd) { return runTodoBrowse(cmd) }`, else falls through to the unchanged classic body.
3. `runTodoBrowse` (`todo_browse.go:36-59`) builds a `[]components.TodoItem` from the same data the classic path uses, constructs the component (`components.NewTodoBrowser(...)`, `.Show(items, callback)`), and drives it via `components.RunPrompt[[]components.TodoItem](browser)` with **zero opts** (real terminal in production).
4. The component (`TodoBrowser`) itself is `Prompt[[]TodoItem]`-conformant and does its own writes per-keypress through an injected closure (`MarkDoneFunc`), not via a single terminal "submit" — this differs from what fnqs.7 needs (single Wizard.Result() at the end), but the file-organization and dispatch-predicate pattern applies directly.

`internal/cli/checklist_run.go` is the second precedent (fnqs.12, `checklist run`), same shape: single component via `RunPrompt`, guard inside.

**No existing CLI call site uses `Wizard`/`Step[T]` composition** — the only real usage examples of `NewWizard`+`Step[T]` are the component-level tests in `internal/tui/components/wizard_test.go`. fnqs.7 is the first ticket to actually chain multiple `Prompt[T]` steps from `internal/cli`.

**Blocker, load-bearing**: `noteCreateCmd`'s `Args: cobra.MinimumNArgs(1)` (`note_v1.go:81`) rejects a bare `rk note create` invocation with a cobra usage error **before `RunE` ever runs** — the wizard code the ticket asks for is unreachable until this validator is loosened (e.g. to `cobra.ArbitraryArgs`), with `runNoteCreateE`'s 0-args non-TTY/`--no-input` case then needing its own explicit error (today that state literally cannot occur, so there's no existing behavior to preserve). `todoAddCmd`/`addCmd` already accept 0 args, so no such change is needed there.

`createNote` is already the converge point for note create. `addDurableTodo`/`addEphemeralTodo` and `appendLogEntry` are the equivalent converge points for the other two verbs — the wizard path should call these exact functions with wizard-collected values, not duplicate their logic.

`writeFileAtomic(path string, data []byte) error` — `internal/cli/adopt.go:249` — shared atomic-write primitive all three create paths route through (via `NewNode → Render → Parse → writeFileAtomic`).

## 5. Subject/body convention (fnqs.5, PR #167, commit a210835)

Lives in `assembleBody` — `internal/cli/body_entry.go:49-114`. Exactly one entry source may be active: positional args, repeatable `-m`, `--edit` (`$EDITOR`), or stdin `-`. For the `-m` path with `requireSubject=true` (todo add's case):

- `messages[0]` is the subject; individually `strings.TrimSpace`-checked non-empty (`body_entry.go:69-71`, error: `"subject (first -m) must not be empty"`).
- Every message is trimmed, then all are joined with `"\n\n"` and the whole result is trimmed again (`body_entry.go:72-76`): `strings.TrimSpace(strings.Join(trimmed, "\n\n"))`.
- The resulting single string is what's passed as `body` into `addDurableTodo`/`node.NewNode` — **there is no separate subject field on the node**; subject and body are pre-concatenated by this convention before the node layer ever sees them.

For the wizard, subject and body arrive as two separate strings (subject step, `TextEditor`/body step). Convergence formula to replicate exactly: `finalBody := strings.TrimSpace(subject); if bodyText := strings.TrimSpace(body); bodyText != "" { finalBody += "\n\n" + bodyText }`. `rk add`'s quick-capture path (`requireSubject=false`) has no subject concept — its convergence is just `strings.TrimSpace(capturedLine)`, mirroring the positional-args branch (`body_entry.go:65-66`, `strings.TrimSpace(strings.Join(args, " "))`).

## 6. REVIEW_PATTERNS.md / prior-review pitfalls relevant here

- **Closure-capture bug** (`docs/REVIEW_PATTERNS.md:117-135`, historically the single most common finding — 18 occurrences): don't capture a mutable field directly inside a `tea.Cmd` closure; capture the value first. Directly relevant to any `StepFactory` closure that reads `prior[...]` or any `MarkDoneFunc`-style closure the wizard's convergence code writes.
- **Nil component access** (`REVIEW_PATTERNS.md:147-161`): guard optional component pointers before calling methods on them.
- From fnqs.6's own review (`ticket-work/reckon-fnqs.6/review.md`), notes explicitly flagged as forward-looking traps for fnqs.7:
  - **R1** (`review.md:57-72`): `Step[T]` factories' priming `tea.Cmd` (e.g. `textInput.Focus()`'s blink) is silently dropped — `Init()` is a no-op on every component; real priming happens synchronously inside `Show()`. This is fine only because no current component does real async work in `Show()`. Keep any new component's priming synchronous, or this silently breaks.
  - **R2** (`review.md:74-81`): `RunPrompt`'s host doesn't check `Done()` right after `Init()` — a `Prompt` that's already terminal at mount time will hang until the first keypress. Only reachable via a degenerate 0-step `Wizard` or a reused-without-`Show()` component; keep every wizard step non-empty and every factory calling `Show()`.
  - **R3** (`review.md:83-89`): `promptGuard`'s error text ("...pass `--no-input` or run from an interactive terminal") is misleading on a genuine non-TTY, since `--no-input` produces the *same* error there — explicitly called out as "fnqs.7's job" to give verb-specific flag guidance if the message is revisited.
- `internal/cli/AGENTS.md:229-260` ("Interactive vs Non-Interactive" / "Interactive Prompts") is **stale generic guidance predating fnqs.6** — its sketch (`if len(args) == 0 { return launchInteractiveForm() }`, a naive `isTTY()` via `os.Stdout.Stat()` only) doesn't match the real, already-built `isInteractive`/`PromptGuard`/`todoListWantsTUI`-style dispatch machinery. Don't follow it; follow §2 above instead. (No `internal/tui/AGENTS.md` currently exists, despite being referenced as a target by REVIEW_PATTERNS.md.)

## 7. Test patterns for TTY-dependent code

Two separate layers, never combined in one test (no PTY is available in CI):

- **CLI dispatch layer** (`internal/cli/todo_test.go:1591-1715`, `internal/cli/interactive_test.go`): stub the package var `isInteractive = func() bool {...}` (save/restore via `t.Cleanup`), then drive the real command through `RootCmd.Execute()` via a helper like `runTodo(t, vault, args...)` (`todo_test.go:112-121`, sets `RootCmd.SetArgs`/`SetOut`/`SetErr`, calls `Execute()`). Assertions check either: the classic-path output content, the *absence* of ANSI escapes (`strings.Contains(out, "\x1b[")`) to prove the TUI never opened, or that the error text mentions `--no-input`/terminal (proving the dispatch reached `PromptGuard` and stopped there — `TestTodoList_Interactive_NoInputErrors`, `todo_test.go:1623-1649`). **No CLI-level test drives an actual interactive session to completion** — 6k0l's own review calls this out explicitly as an accepted, non-blocking gap (`ticket-work/reckon-6k0l/review.md`, "Testing — end-to-end TUI dispatch coverage gap [INFERRED, acceptable]").
- **Component layer** (`internal/tui/components/prompt_test.go`, `wizard_test.go`): drive the real `RunPrompt`/`Wizard.Run` with `tea.WithInput(bytes.NewReader(scriptedKeys))` / `tea.WithOutput(io.Discard)` opts, wrapped in the timeout-bounded helper `runPromptForTest[T any](t *testing.T, fn func() (T, bool, error))` (`prompt_test.go:40-62`, 5s timeout, fails fast instead of hanging `go test` on a bad keystroke script).
- **Pure business logic**, tested directly with no bubbletea involvement at all: e.g. `buildTodoItems`/`makeMarkDoneFunc` (`todo_test.go:1717-1900+`) call the plain Go functions the TUI's callbacks wrap, asserting on-disk file state directly.

**Implication for fnqs.7's "writes the identical file" acceptance criterion**: don't try to prove this via one end-to-end keystroke-driven CLI test (no precedent, no PTY). Instead (a) extract a pure "wizard result map → verb params" conversion function and unit-test it directly against both a synthetic `map[string]any` (bypassing bubbletea) and against the flag-driven path's own params struct/call, so both paths provably converge on the same `addDurableTodo`/`createNote`/`appendLogEntry` call; (b) cover actual keystroke-driven wizard assembly at the component layer per `wizard_test.go`'s pattern; (c) cover CLI dispatch routing (bare+TTY attempts interactive, any arg/flag stays classic) per §7's first bullet.

## 8. Other open items for the planner

- **[OPEN]** Which flags gate "bare" for `todo add`/`add`? `todoListWantsTUI` only checks *output-shaping* flags for `list`; for a *create* verb, every input flag (`--scheduled/--deadline/--depends/--repeat/--author/-m/--edit/--ephemeral` for todo add; `--author/--at/-m/--edit` for add) plausibly must also gate, per the ticket's literal "with args/flags, behavior stays non-interactive." Recommend mirroring `resetTodoFlags`'s existing flag-name lists (`todo.go:74`) for the "any Changed" check.
- **[OPEN]** `--ephemeral` on `rk todo add`: the ticket's wizard steps (subject→body→scheduled→deadline→depends) only describe the **durable** path. Recommend: wizard always creates a durable todo; `--ephemeral` stays flag-only (any flag already routes non-interactive per the point above, so this falls out naturally — just confirm intentionally with the planner, don't leave it implicit).
- **[OPEN]** depends picker's row source: mirror `todo_browse.go`'s `buildTodoItems`/`listDurableTodos` (`todo.go:511`) pattern to open the index, list open durable todos, map to `[]components.IndexRow`. `--depends` is otherwise unvalidated today (`todo.go:375-377` sets the link with no existence check) — the picker path incidentally makes this safer since it only offers rows that exist, but that's a UX bonus, not a requirement to newly enforce for the flag path.
- **[INFERRED]** `noteBodyFlag`'s doc comment says body "may contain [[wikilinks]]" (`note_v1.go:129`) — confirms wikilinks are the only mechanism notes have for outbound links; there is no structured `Links` concept elsewhere in `noteCreateParams` or `node.NewNode` to converge on.
